# Ролі користувачів

> **Важливо.** У системі **немає** облікових записів, автентифікації та розмежування прав. Роль визначається лише тим, хто має доступ до комп’ютера з програмою, до файлів конфігурації та до мережевого порту API. Нижче описано ролі за способом використання (фактична модель) і рекомендовані права, до яких слід прийти після впровадження автентифікації.

## 1. Ролі

| Роль | Хто це | Як взаємодіє із системою |
|---|---|---|
| **Користувач (власник скриньки)** | Людина, чия поштова скринька обробляється | Запускає графічний інтерфейс, переглядає аналітику та сповіщення, підтверджує або виправляє категорії листів |
| **Адміністратор / налаштовувач** | Той, хто розгортає і налаштовує систему (часто та сама особа) | Задає облікові дані Gmail, редагує конфігурацію й пороги, керує категоріями та правилами автоматизації, запускає API, обслуговує бази даних |
| **Клієнт API** | Мобільний застосунок або інший сервіс | Викликає REST-ендпоінти `/api/...` для класифікації, пошуку, відгуків, перегляду звітів |
| **Системний планувальник** | Фоновий процес автоматизації (бібліотека `schedule`) | Виконує правила автоматизації без участі людини: мітки, зірочки, архівування, створення завдань |

## 2. Матриця прав

Позначки: ✔ — дозволено за задумом; ✖ — не передбачено. Колонка «Фактично» описує поточну реалізацію.

| Дія | Користувач | Адміністратор | Клієнт API | Планувальник | Фактично |
|---|:-:|:-:|:-:|:-:|---|
| Переглядати аналітику та панель | ✔ | ✔ | ✔ | ✖ | Без перевірки прав (GUI, `/api/dashboard`, `/api/analytics/daily`) |
| Класифікувати лист | ✔ | ✔ | ✔ | ✔ | Без перевірки прав (`/api/classify`) |

| Надсилати відгук для навчання | ✔ | ✔ | ✔ | ✖ | Без перевірки прав (`/api/learning/feedback`) |

## 3. Рекомендації щодо впровадження ролей

1. Увести автентифікацію API (ключ або токен у заголовку `Authorization`) і відхиляти запити без нього кодом `401`.
2. Розділити права API мінімум на два рівні:
   - **читання** — `GET`-ендпоінти, класифікація, пошук;
   - **адміністрування** — `POST /api/categories`, `POST /api/automation/rules`.
   Недостатньо прав — код `403`.
3. Обмежити, хто може вмикати дії `trash` та `archive` в автоматизації: це єдина функція, що змінює дані в скриньці незворотно.
4. Записувати в журнал, хто і коли змінив правила та пороги (у `security_compliance.py` вже є таблиця `access_log`).

Тести прав доступу: TC-03 з лабораторної роботи №5 очікує відповідь `401/403` на запит без автентифікації.
