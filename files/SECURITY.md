# Політика безпеки

Проєкт працює з поштовою скринькою, паролем додатка та персональними даними з листів, тому безпеці приділено окремий документ. Стан описано за результатами аналізу коду та перевірки залежностей станом на 13.11.2026.

## Підтримувані версії

Підтримується лише поточний стан основної гілки. Окремих релізів немає.

## Як повідомити про вразливість

Не створюйте публічний issue з деталями вразливості. Скористайтеся приватним повідомленням: вкладка **Security → Report a vulnerability** у GitHub-репозиторії (якщо функція ввімкнена) або зв’яжіться з власником репозиторію напряму. Опишіть кроки відтворення, версію (коміт) і можливі наслідки.

## Відомі проблеми безпеки

Це відомі невиправлені проблеми. Не розгортайте систему поза локальним комп’ютером, доки не усунуто пункти 1–3.

| № | Проблема | Серйозність | Де | Рекомендація |
|---|---|---|---|---|
| 1 | REST API не має автентифікації. Сервер слухає `0.0.0.0`, CORS відкритий для всіх джерел | Критична | `mobile_api.py` | Додати перевірку ключа/токена; слухати лише `127.0.0.1`; обмежити CORS конкретними адресами |
| 2 | При запуску `python mobile_api.py` вмикається `debug=True` (інтерактивний налагоджувач Werkzeug) | Критична | `mobile_api.py`, кінець файлу | Запускати через WSGI-сервер із `debug=False` (див. [DEPLOYMENT.md](docs/DEPLOYMENT.md)) |
| 3 | Відповіді API з помилкою містять текст винятку (`str(e)`), тобто внутрішні деталі | Середня | усі ендпоінти `mobile_api.py` | Повертати загальне повідомлення, деталі писати в журнал |

| 5 | Шифрування облікових даних використовує фіксовану сіль (`gmail_ai_salt_2024`) | Середня | `utilities/credential_manager.py` | Генерувати випадкову сіль для кожного файлу й зберігати разом із шифротекстом |

| 7 | У репозиторії є персональні дані: навчальні дані (`data/email_training_data.*`) з відправниками та темами листів, приклади з реальною адресою одержувача, журнал pip із локальним шляхом у `archive/1.24.0` | Середня | `data/`, `master_gmail_ai.py`, `archive/` | Видалити з історії Git (див. нижче), замінити приклади вигаданими даними |
| 8 | Закріплені залежності мають відомі вразливості (див. нижче) | Висока | `requirements.txt` | Оновити пакети й перевірити сумісність |
| 9 | Користувацьких ролей немає: кожен, хто має доступ до API чи файлів, має повні права | Висока | уся система | Див. [docs/ROLES.md](docs/ROLES.md) |

### Залежності

Команда `pip-audit -r requirements.txt` повідомила про відомі вразливості в п’яти закріплених пакетах:

| Пакет | Закріплена версія | Мінімальна версія з виправленням |
|---|---|---|
| cryptography | 41.0.7 | 49.0.0 (для всіх знайдених записів) |
| Flask | 3.0.3 | 3.1.3 |
| Flask-Cors | 5.0.0 | 6.0.0 |
| nltk | 3.9.1 | 3.10.0 (для частини записів; повний перелік дивіться в звіті інструмента) |
| python-dotenv | 1.1.0 | 1.2.2 |

Оновлення мажорних версій може порушити сумісність (особливо `cryptography`, `scikit-learn` і збережена модель `smart_model.pkl`), тому після оновлення виконайте регресійні перевірки. Регулярно запускайте:

```bash
pip install pip-audit
pip-audit -r requirements.txt
```

## Що вже зроблено правильно

- Облікові дані зберігаються окремо від коду; `.gitignore` виключає `.env`, `*.db`, `*.pkl`, журнали.
- З поштою з’єднання виконується через IMAP по SSL (`imap.gmail.com:993`).
- Є можливість зберігати облікові дані у зашифрованому вигляді (Fernet, PBKDF2-HMAC-SHA256, 100 000 ітерацій).
- SQL-запити в `/api/search` параметризовані (захист від SQL-ін’єкцій у переглянутому коді).
- Використовується пароль додатка, а не основний пароль облікового запису.

## Правила безпечного використання

1. Використовуйте **лише пароль додатка** Gmail. Основний пароль у систему вводити не можна.
2. Не комітьте `credentials/gmail_credentials.env`, бази `*.db`, модель `*.pkl`, журнали та навчальні дані.
3. Обмежте права на файли з паролями. Linux/macOS: `chmod 600 credentials/gmail_credentials.env`. Windows: залиште доступ лише власному користувачу.
4. Для шифрованих облікових даних задавайте `GMAIL_AI_MASTER_PASSWORD` через змінну середовища процесу, а не у файлі в репозиторії.
5. API запускайте тільки на `127.0.0.1`. Для доступу ззовні — лише через зворотний проксі з TLS і автентифікацією.
6. На початку працюйте в режимі DEMO / з вимкненим `auto_archive_spam`. Автоматичні дії вмикайте після перевірки на тестовій скриньці.
7. Тестуйте на окремому тестовому обліковому записі Gmail, а не на робочій пошті.
8. Якщо пароль додатка потрапив у публічний доступ, негайно відкличте його на <https://myaccount.google.com/apppasswords> і створіть новий.

## Якщо персональні дані вже потрапили в репозиторій

Додавання файлу в `.gitignore` не видаляє його з історії.

```bash
# прибрати з поточного індексу, залишивши локально
git rm --cached data/email_training_data.csv data/email_training_data.json
git rm -r --cached analytics_output archive
git commit -m "Remove personal data from tracking"

# прибрати з усієї історії (потрібен git-filter-repo)
git filter-repo --path data/email_training_data.csv --path data/email_training_data.json --invert-paths
git push --force
```

Після перезапису історії всі, хто клонував репозиторій, мають клонувати його заново. Якщо в даних були реальні паролі або токени — вважайте їх скомпрометованими й змініть.
